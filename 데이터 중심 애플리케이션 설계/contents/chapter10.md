# 10장. 일괄 처리

1부와 2부에서는 요청·질의가 들어오고 그에 대한 응답이 나가는 시스템을 다뤘다. 이런 종류의 시스템을 **서비스(온라인 시스템)** 라 부른다. 그러나 시스템을 구축하는 방식은 이것만이 아니다. 이 장에서 다룰 세 가지 유형은 다음과 같다.

- **서비스(온라인 시스템):** 클라이언트 요청이 도착하기를 기다렸다가 가능한 빨리 응답한다. **응답 시간**이 주된 성능 지표이며, 가용성이 매우 중요하다.
- **일괄 처리 시스템(오프라인 시스템):** 매우 큰 입력 데이터를 받아 잡(job)을 수행하고 결과 데이터를 생산한다. 잡은 몇 분에서 며칠까지 걸리므로 보통 사용자가 응답을 기다리지 않는다. 주된 성능 지표는 **처리량(throughput)** 이다.
- **스트림 처리 시스템(준실시간 시스템):** 온라인과 오프라인의 중간이다. 일괄 처리처럼 입력을 소비해 출력을 생산하지만, 요청에 응답하는 것이 아니라 **이벤트가 발생한 직후** 처리한다. 11장에서 다룬다.

일괄 처리는 신뢰성 있고 확장성 있으며 유지보수하기 좋은 애플리케이션을 구축하는 데 매우 중요한 요소다. 2004년 구글이 발표한 **맵리듀스(MapReduce)** 는 "엄청난 규모로 확장 가능하면서 상용 하드웨어에서 동작하는 단순한 프로그래밍 모델"로 큰 영향을 미쳤다. 맵리듀스를 이해하는 가장 좋은 출발점은, 놀랍게도 40년 전에 나온 **유닉스 도구**다.

## 유닉스 도구로 일괄 처리하기
### 단순 로그 분석
웹 서버 접근 로그에서 가장 인기 있는 페이지 상위 5개를 뽑는다고 하자. 유닉스에서는 다음 한 줄이면 된다.

```bash
cat /var/log/nginx/access.log |
  awk '{print $7}' |      # 요청 URL만 추출
  sort             |      # 알파벳순 정렬
  uniq -c          |      # 중복 제거하며 등장 횟수 세기
  sort -r -n       |      # 횟수 기준 내림차순 정렬
  head -n 5               # 상위 5개만 출력
```

이 파이프라인은 **놀랄 만큼 강력하다.** 수 기가바이트 로그 파일도 몇 초 만에 처리하고, 필요하면 중간에 필터를 끼워 넣어 손쉽게 분석을 바꿀 수 있다.

#### 연쇄 명령 대 커스텀 프로그램
같은 일을 루비나 파이썬 스크립트로 짤 수도 있다. URL을 키로, 등장 횟수를 값으로 하는 **인메모리 해시 테이블**을 유지하면 된다. 이 방식은 정렬 과정이 없어 짧은 작업 목록에는 더 빠르다.

두 방식의 큰 차이는 **작업 세트가 메모리보다 커질 때** 드러난다.

- **인메모리 집계:** 고유 URL 수가 적으면 잘 동작한다. 그러나 고유 키가 메모리에 다 안 들어가면 곧바로 무너진다.
- **정렬 기반 접근법(유닉스 파이프라인):** GNU `sort`는 메모리보다 큰 데이터셋을 **디스크로 자동 spill** 하고, 여러 CPU 코어로 **자동 병렬 정렬**한다. 즉, 병목이 디스크로 옮겨갈 뿐 규모가 커져도 그냥 동작한다.

### 유닉스 철학
이런 파이프라인이 가능한 이유는 1970년대 유닉스 설계자들이 세운 **유닉스 철학** 덕분이다.

1. 각 프로그램이 **한 가지 일만 하도록** 만든다. 새 작업이면 새 프로그램을 만든다.
2. 모든 프로그램의 출력이 **다른 프로그램의 입력**이 될 수 있게 한다.
3. 소프트웨어를 **빠르게 시도**해 보게 만든다. 서투른 부분은 버리고 다시 만든다.

이는 오늘날의 **애자일**, **데브옵스**, 그리고 마이크로서비스의 조합 가능성(composability)과 놀랍도록 닮았다.

#### 동일 인터페이스
프로그램 A의 출력이 프로그램 B의 입력이 되려면 **같은 인터페이스**를 써야 한다. 유닉스에서 그 인터페이스는 **파일(정확히는 파일 서술자)**, 즉 순서가 있는 바이트의 열이다. 대부분의 유닉스 도구는 이 바이트 열을 **줄바꿈으로 구분된 레코드 목록**으로 취급하고, `\t`나 공백으로 필드를 나눈다.

이 인터페이스가 완벽하진 않지만(파싱은 조잡하다), 수십 년간 **서로 다른 도구들이 조합될 수 있게** 만든 결정적인 요인이다. 반면 오늘날의 데이터베이스들은 서로 다른 프로토콜을 쓰므로 파이프로 이어 붙일 수 없다.

#### 로직과 연결의 분리
유닉스 도구는 표준 입력(stdin)과 표준 출력(stdout)을 사용한다. **프로그램은 입력이 어디서 오는지, 출력이 어디로 가는지 신경 쓰지 않는다.** 이것이 **느슨한 결합(loose coupling)**, **높은 응집도(high cohesion)** 를 만든다.

물론 한계도 있다. 입력이 여럿이거나 출력이 여럿인 프로그램은 다루기 까다롭고, 파이프는 **한 장비 안에서만** 동작한다.

#### 투명성과 실험
유닉스 도구가 성공한 이유 중 하나는 **무슨 일이 일어나는지 보기 쉽다**는 점이다.

- 입력 파일은 보통 **불변(immutable)** 으로 취급된다. 그래서 명령을 몇 번이고 다시 실행해도 안전하다.
- 파이프라인 어느 지점에서든 끊어서 `less`로 중간 결과를 눈으로 확인할 수 있다.
- 특정 단계의 결과를 파일로 저장해 두고, 그다음 단계부터 다시 시작할 수 있다. 즉 **재시작 비용이 낮다.**

유닉스 도구의 가장 큰 제약은 **단일 장비에서만 실행된다**는 점이다. 그리고 바로 그 지점에서 하둡 같은 도구가 필요해진다.

## 맵리듀스와 분산 파일 시스템
맵리듀스는 유닉스 도구와 비슷하지만 **수천 대의 장비로 분산**된다. 유닉스 도구가 stdin/stdout을 쓰는 것처럼, 맵리듀스 잡은 **분산 파일 시스템의 파일**을 읽고 쓴다. 하둡에서 그 파일 시스템이 **HDFS(Hadoop Distributed File System)** 다.

HDFS는 **비공유(shared-nothing)** 원칙을 따른다. 특별한 하드웨어가 필요 없고, 일반 데이터센터 네트워크로 연결된 상용 컴퓨터들을 쓴다.

- 각 장비에서 데몬 프로세스가 실행되어 그 장비의 디스크를 네트워크에 노출한다.
- **네임노드(NameNode)** 라는 중앙 서버가 어떤 파일 블록이 어떤 장비에 저장됐는지 추적한다.
- 장비나 디스크 장애를 견디기 위해 파일 블록은 여러 장비에 **복제**된다(복제 또는 이레이저 코딩).

이 구조 덕분에 HDFS는 수만 대 장비에 걸쳐 **수백 페타바이트**까지 확장됐다. 상용 하드웨어와 오픈소스 소프트웨어의 조합이라 비용도 훨씬 저렴하다.

### 맵리듀스 잡 실행하기
맵리듀스는 프로그래밍 프레임워크다. HDFS 같은 분산 파일 시스템 위에서 대용량 데이터셋을 처리하는 코드를 작성한다. 앞서 본 로그 분석 예제와 패턴이 유사하다.

1. 입력 파일을 읽어 **레코드**로 쪼갠다.
2. **매퍼(mapper)** 함수를 호출해 각 레코드에서 키와 값을 추출한다.
3. 키를 기준으로 모든 키-값 쌍을 **정렬**한다.
4. **리듀서(reducer)** 함수를 호출한다. 같은 키를 가진 값들을 한꺼번에 반복 처리할 수 있다.

여기서 매퍼와 리듀서만 개발자가 작성한다.

- **매퍼:** 입력 레코드마다 **한 번씩** 호출된다. 입력에서 키와 값을 추출한다. 상태를 유지하지 않으므로 레코드마다 독립적이다.
- **리듀서:** 매퍼가 만든 키-값 쌍을 받아, 같은 키를 가진 값들을 모아 반복자로 넘겨받는다. 이 값들로 출력 레코드를 만든다.

정렬 단계(3번)는 프레임워크가 수행한다. 매퍼의 출력은 **항상 리듀서에 넘기기 전에 키로 정렬**된다.

#### 맵리듀스의 분산 실행
유닉스 파이프라인과 달리 맵리듀스는 **여러 장비에 걸쳐 병렬 실행**된다. 핵심 아이디어는 **연산을 데이터 가까이 옮기는 것(putting the computation near the data)** 이다.

- **입력 파일의 블록이 있는 장비에서 매퍼를 실행한다.** 네트워크로 데이터를 옮기지 않으므로 네트워크 부하가 줄고 지역성(locality)이 높아진다. 코드(JAR 파일)는 데이터보다 훨씬 작으므로 코드를 옮기는 편이 싸다.
- 리듀스 태스크 수는 사용자가 설정한다. 어떤 리듀서로 갈지는 **키의 해시**로 결정한다(같은 키는 항상 같은 리듀서로).
- 매퍼는 결과를 정렬한 뒤 로컬 디스크에 쓰고, 리듀서는 각 매퍼로부터 자기 파티션의 파일을 가져와 병합한다. 이 과정을 **셔플(shuffle)** 이라 부른다.

#### 맵리듀스 워크플로
맵리듀스 잡 하나로 풀 수 있는 문제는 제한적이다. 그래서 잡을 **연결(chain)** 해 **워크플로**로 엮는 것이 일반적이다. 하둡 맵리듀스에는 워크플로 개념이 따로 없어서, 한 잡의 출력 디렉터리를 다음 잡의 입력 디렉터리로 지정하는 **암묵적 의존성**으로 연결한다.

- 이 방식은 유닉스 파이프와 다르다. 파이프는 스트리밍이지만, 잡 연결은 **선행 잡이 완전히 끝나야** 다음 잡이 시작된다.
- 이런 의존성 관리를 위해 **워크플로 스케줄러**(우지, 아즈카반, 루이지, 에어플로, 핀볼 등)가 개발됐다.
- 하이브, 피그, 캐스캐이딩, 크런치 같은 고수준 도구는 여러 맵리듀스 잡을 자동으로 엮어 준다.

### 리듀스 사이드 조인과 그룹화
일괄 처리에서도 **조인**은 흔하다. 예를 들어 사용자 활동 이벤트 로그와 사용자 프로필 데이터베이스를 조인해 "어떤 연령대가 어떤 페이지를 좋아하는지" 분석한다고 하자.

가장 단순한 구현은 활동 이벤트를 하나씩 읽으며 **데이터베이스에 원격 질의**하는 것이다. 그러나 이는 나쁜 선택이다.

- 처리량이 **끔찍하게 나쁘다.** 네트워크 왕복 지연에 종속되고, 데이터베이스에 과부하를 준다.
- **결정적(deterministic)** 이지 않다. 그 사이 데이터가 바뀌면 재실행 시 결과가 달라진다.

더 나은 접근은 **데이터베이스 사본을 추출해 분산 파일 시스템에 넣는 것**이다. 그러면 조인은 순수하게 로컬 디스크·네트워크 대역폭 문제가 되고, 결정적으로 동작한다.

#### 정렬 병합 조인
- 한 매퍼는 활동 이벤트에서 `(사용자 ID, 활동 이벤트)`를 추출하고, 다른 매퍼는 사용자 DB에서 `(사용자 ID, 생년월일)`을 추출한다.
- 프레임워크가 키(사용자 ID)로 정렬·파티셔닝하므로, **같은 사용자 ID의 레코드는 모두 같은 리듀서로 인접해 도착**한다.
- **보조 정렬(secondary sort)** 로 사용자 프로필 레코드가 활동 이벤트보다 먼저 오게 하면, 리듀서는 프로필을 변수에 담아 두고 이어 오는 활동 이벤트마다 조인 결과를 출력하면 된다.

이 알고리즘을 **정렬 병합 조인(sort-merge join)** 이라 한다.

#### 관련 데이터를 한곳에 모으기
맵리듀스는 **레코드를 어디로 보낼지(키)** 와 **거기서 무엇을 할지(리듀서 로직)** 를 깔끔히 분리한다. 네트워크 통신을 애플리케이션 코드에서 분리해 준다는 점이 중요하다. 애플리케이션 코드는 **어떤 태스크가 실패해서 재시도됐는지 걱정할 필요가 없다.** 프레임워크가 알아서 보장한다.

#### 그룹화
`GROUP BY`도 같은 방식이다. 그룹화할 키를 매퍼가 방출하면, 같은 키를 가진 레코드가 같은 리듀서에 모인다. 세션화(sessionization) 같은 작업이 대표적이다.

#### 쏠림 다루기
한 키에 데이터가 지나치게 많이 몰리면(유명인의 팔로워처럼) 문제가 생긴다. 이를 **쏠림(skew)** 또는 **핫스팟**이라 부르고, 그런 키를 **린치핀 객체(linchpin object)** 라 한다. 하나의 리듀서가 다른 모든 리듀서보다 훨씬 오래 걸려 전체 잡이 그 리듀서를 기다리게 된다.

- **피그의 편중 조인(skewed join):** 샘플링 잡으로 핫 키를 미리 찾고, 그 키의 레코드는 **여러 리듀서에 무작위로 분산**한다. 반대쪽 입력은 해당 키를 **모든 리듀서로 복제**한다.
- **하이브의 스큐 조인:** 핫 키를 메타데이터에 명시하고, 그런 키는 맵 사이드 조인으로 처리한다.

### 맵 사이드 조인
리듀스 사이드 조인은 입력 데이터에 대한 가정이 필요 없다는 장점이 있지만, **정렬·복사·병합에 드는 비용이 상당하다.** 입력에 대해 특정 가정을 할 수 있다면 **맵 사이드 조인**으로 리듀스 단계를 완전히 없앨 수 있다.

- **브로드캐스트 해시 조인:** 조인 대상 중 한쪽이 **메모리에 들어갈 만큼 작을 때** 쓴다. 각 매퍼가 작은 쪽을 통째로 읽어 **인메모리 해시 테이블**로 만들고, 큰 쪽을 스캔하며 조회한다. "작은 쪽을 모든 매퍼에 브로드캐스트한다"는 의미다.
- **파티션 해시 조인:** 양쪽 입력이 **같은 방식(같은 키, 같은 파티션 수)으로 파티셔닝**돼 있다면, 각 매퍼는 자기 파티션에 해당하는 부분만 읽으면 된다. 해시 테이블에 담아야 할 데이터가 1/n로 줄어든다. 하이브에서는 **버킷 맵 조인(bucketed map join)** 이라 부른다.
- **맵 사이드 병합 조인:** 파티셔닝에 더해 **같은 키로 정렬까지** 돼 있다면 해시 테이블조차 필요 없다. 두 입력 파일을 나란히 스캔하며 병합하면 된다.

맵 사이드 조인은 물리적 레이아웃에 대한 가정이 필요하므로, 이런 메타데이터(파티션 수, 정렬 여부)를 **하이브 메타스토어** 같은 곳에서 관리하는 것이 중요하다.

### 일괄 처리 워크플로의 출력
일괄 처리는 OLTP도 아니고 분석도 아닌 중간 어딘가에 있다. 그렇다면 결과는 어디로 가야 할까?

#### 검색 색인 구축
구글이 맵리듀스를 만든 원래 용도가 **검색 색인 구축**이었다. 문서 집합에 대해 매퍼가 필요한 대로 파티셔닝하고, 리듀서가 파티션별 색인을 만들어 분산 파일 시스템에 기록한다. 색인 파일은 **불변**이므로, 문서가 바뀌면 전체를 다시 만들거나(주기적 전체 재빌드) 세그먼트 병합으로 증분 갱신한다.

#### 키-값 저장소로 출력하기
머신러닝 시스템(분류기, 추천 시스템)의 출력처럼, 결과를 서비스에서 조회할 수 있어야 하는 경우가 있다. 이때 **일괄 처리 잡이 데이터베이스에 직접 레코드를 하나씩 쓰는 것은 나쁜 생각**이다.

- 레코드마다 네트워크 요청을 보내면 **처리량이 형편없다.**
- 태스크가 재시도되면 **같은 레코드가 여러 번 쓰인다.** 부분적으로만 완료된 상태가 외부에 노출된다.
- 일괄 처리의 병렬성이 그대로 데이터베이스 부하가 되어 **운영 중인 데이터베이스를 압도**할 수 있다.

훨씬 나은 방법은 잡 안에서 **완전히 새로운 데이터베이스 파일을 통째로 만들고**, 완성된 파일을 서비스 중인 서버로 **원자적으로 로드**하는 것이다. 볼드모트, 엘리펀트DB, HBase 대량 적재 등이 이 방식을 지원한다.

#### 일괄 처리 출력의 철학
이 방식은 앞서 본 유닉스 철학과 정확히 같다.

- **입력은 불변으로 취급하고, 출력은 새로 만든다.** 코드에 버그가 있어 잘못된 출력을 냈다면, 코드를 고치고 잡을 다시 실행하면 그만이다. 즉 이전 출력으로 **롤백하기 쉽다.**
- 이 되돌릴 수 있는 성질을 **인적 내결함성(human fault tolerance)** 이라 부른다. 실수를 되돌리기 쉬우면 **기능 개발이 빨라진다.**
- **관심사의 분리:** 코드를 작성한 팀이 그 코드가 만든 오류를 반드시 처리해야 하는 것은 아니다. 프레임워크가 실패·재시도를 처리하고, 실패한 태스크의 출력은 조용히 버려진다.

### 하둡과 분산 데이터베이스의 비교
맵리듀스의 아이디어는 새롭지 않다. 병렬 조인 알고리즘은 MPP(대규모 병렬 처리) 데이터베이스가 10년 앞서 구현했다. 그렇다면 차이는 무엇인가?

- **저장소의 다양성:** MPP 데이터베이스는 데이터를 넣기 전에 **신중한 모델링과 스키마 설계**를 요구한다. 하둡은 어떤 형식이든 HDFS에 **그냥 덤프**할 수 있게 한다. 데이터를 빨리 모으는 것이 중요하고 해석은 나중에 미룬다는 아이디어(**스시 원칙 — 원시 데이터가 더 좋다**)다. 이렇게 만든 저장소를 **데이터 레이크**라 부르며, 데이터 해석은 소비자의 문제가 된다(**읽기 스키마**).
- **처리 모델의 다양성:** MPP 데이터베이스는 SQL 질의에 최적화돼 있지만, 모든 처리가 SQL로 표현되지는 않는다. 머신러닝, 추천 시스템, 이미지 분석, 전문 색인 같은 작업에는 **임의의 코드**가 필요하다. 맵리듀스는 그런 코드를 대용량 데이터셋 위에서 실행하게 해 주며, 그 위에 SQL 질의 엔진(하이브)도 얹을 수 있다.
- **빈번한 결함을 견디게 설계:** MPP 데이터베이스는 질의 하나가 실패하면 보통 **질의 전체를 재시도**한다. 맵리듀스는 **개별 태스크 단위로 재시도**하며, 중간 상태를 디스크에 기록한다. 이는 구글의 환경(우선순위가 높은 작업이 낮은 작업을 **선점(preemption)** 해 강제 종료하는 과도한 자원 공유 환경)에서 나온 설계다. 태스크 하나가 죽어도 잡 전체를 다시 하지 않는다.

## 맵리듀스를 넘어
맵리듀스는 이해하기 쉽지만 **직접 쓰기에는 매우 힘들다.** 그래서 그 위에 하이브·피그·캐스캐이딩·크런치 같은 고수준 도구가 만들어졌고, 나아가 다른 실행 모델도 등장했다.

### 중간 상태 구체화
맵리듀스 잡은 출력을 **완전히 구체화(materialize)** 해서 분산 파일 시스템에 쓴다. 유닉스 파이프가 작은 인메모리 버퍼로 **점진적으로 스트리밍**하는 것과 대조적이다. 이 구체화는 여러 단점을 낳는다.

- 맵리듀스 잡은 **선행 잡의 모든 태스크가 끝나야** 시작할 수 있다. 파이프라인 방식이면 출력이 나오는 대로 소비할 수 있다.
- 매퍼가 **불필요한 경우가 많다.** 리듀서 출력을 그대로 다시 읽어 파티셔닝만 하는 매퍼는 리듀서 로직에 합칠 수 있다.
- 중간 상태를 분산 파일 시스템에 저장하면 **여러 장비에 복제**되는데, 임시 데이터치고는 과한 비용이다.

이 문제를 풀기 위해 **스파크(Spark), 테즈(Tez), 플링크(Flink)** 같은 **데이터플로 엔진**이 등장했다.

- 워크플로 전체를 **하나의 잡**으로 다루며, 여러 처리 단계를 **연산자(operator)의 DAG**로 표현한다.
- 매퍼/리듀서 역할을 강제하지 않고, 연산자 간 데이터 전달 방식을 유연하게 고른다. 파티셔닝만 하고 **정렬은 필요할 때만** 한다.
- 불필요한 맵 태스크를 없애고, 스케줄러가 **지역성 최적화**를 할 수 있다.
- 중간 상태를 보통 **메모리나 로컬 디스크**에 두므로 I/O가 훨씬 적고, JVM 프로세스를 **재사용**해 시작 오버헤드를 줄인다.

#### 내결함성
중간 상태를 분산 파일 시스템에 쓰지 않으면 내결함성은 어떻게 확보할까? 데이터플로 엔진은 장비가 죽었을 때 **잃어버린 데이터를 다시 계산**한다. 스파크는 이를 위해 **RDD의 계보(lineage)** 를 추적한다.

단, 재계산으로 복구하려면 연산이 **결정적**이어야 한다. 같은 입력에 항상 같은 출력을 내야 한다. 난수, 해시 테이블 순회 순서, 시스템 시계 같은 비결정적 요소가 끼면 하위 연산자가 모순된 데이터를 보게 되므로 주의해야 한다. 재계산 비용이 큰 중간 데이터는 **구체화하는 편이 나을 수도 있다.**

### 그래프와 반복 처리
페이지랭크 같은 **그래프 알고리즘**은 그래프를 여러 번 순회하는 **반복(iterative) 스타일**이 필요하다. 맵리듀스로 이를 구현하면 매 반복마다 전체 데이터셋을 읽고 쓰므로 극도로 비효율적이다.

**프리글(Pregel)** 모델(**대량 동기식 병렬 — BSP**)은 이를 위한 최적화다.

- 하나의 정점(vertex)이 다른 정점에 **메시지를 보낸다.** 각 반복(슈퍼스텝)에서 정점은 지난 반복에 받은 메시지를 처리하고, 상태를 갱신하고, 이웃에 메시지를 보낸다.
- 맵리듀스와 달리 정점은 **반복 사이에 상태를 기억**한다. 변경된 부분만 처리하면 되므로 훨씬 효율적이다.
- 내결함성은 반복 끝마다 모든 정점 상태를 **체크포인트**로 저장해 확보한다.
- 문제는 **통신 오버헤드**다. 그래프를 잘 파티셔닝하기 어려워 노드 간 메시지가 많이 오간다. 그래서 그래프가 단일 장비 메모리에 들어간다면 **단일 장비 알고리즘이 분산 일괄 처리보다 빠른 경우가 많다.**

### 고수준 API와 언어
데이터플로 엔진이 성숙하면서 관심사는 **사용 편의성**과 **선언적 표현**으로 옮겨 갔다. 하이브, 스파크 DataFrame, 플링크 테이블 API 등이 그렇다.

- 관계형 연산자를 선언적으로 명시하면, **질의 최적화기**가 조인 알고리즘을 고르고 불필요한 단계를 제거할 수 있다.
- 칼럼 지향 저장소 레이아웃과 **벡터화 실행** 같은 최적화를 프레임워크가 적용해 CPU 효율을 높인다.
- 동시에 임의 코드 실행 능력은 그대로 남아 있어, 통계·수치 알고리즘(MADlib), 유전체 분석, 이미지 처리 같은 **도메인 특화 처리**도 같은 인프라 위에서 돌릴 수 있다.

## 정리
이 장에서는 일괄 처리를 살펴봤다. 시작점은 `awk`, `grep`, `sort` 같은 유닉스 도구였고, 그 설계 철학이 맵리듀스와 데이터플로 엔진으로 이어졌다.

- 유닉스 도구는 **불변 입력**, **동일 인터페이스(파일)**, **로직과 연결의 분리**라는 원칙으로 조합 가능성을 얻었다. 맵리듀스와 하둡은 같은 원칙을 **수천 대 장비의 분산 환경**으로 확장한 것이다.
- 분산 일괄 처리 프레임워크가 풀어야 하는 두 가지 핵심 문제는 다음과 같다.
  - **파티셔닝:** 매퍼는 입력 파일 블록 단위로 파티셔닝된다. 매퍼 출력은 키로 파티셔닝·정렬돼 리듀서로 병합된다. 목적은 **관련 데이터를 같은 곳에 모으는 것**이다.
  - **내결함성:** 중간 상태를 디스크에 기록해, 태스크 하나가 실패해도 **그 태스크만 재시도**한다. 데이터플로 엔진은 구체화를 줄이는 대신 **재계산(계보 추적)** 으로 복구한다.
- 주요 조인 알고리즘은 다음과 같다.
  - **정렬 병합 조인:** 양쪽에서 같은 키를 추출해 같은 리듀서로 보내고 병합한다.
  - **브로드캐스트 해시 조인:** 작은 쪽을 인메모리 해시 테이블로 만들어 모든 매퍼에 뿌린다.
  - **파티션 해시 조인:** 양쪽이 같은 방식으로 파티셔닝됐다면 파티션 단위로 해시 조인한다.
- 일괄 처리 잡의 가장 중요한 특징은 **입력을 읽고 출력을 새로 만들며, 입력을 변경하지 않는다**는 점이다. 즉 **부수 효과가 없다.** 이 덕분에 잡을 안전하게 재시도할 수 있고, 잘못된 출력은 코드를 고쳐 다시 실행하는 것만으로 롤백할 수 있다(**인적 내결함성**).
- 일괄 처리의 근본적 한계는 **입력이 유한하다(bounded)** 는 가정이다. 잡은 언젠가 입력 전체를 다 읽고 끝난다. 그러나 현실의 데이터는 끝없이 도착한다.

입력이 끝나기를 기다리지 않고, **이벤트가 발생하는 대로 처리**하려면 어떻게 해야 할까? 이것이 11장 **스트림 처리**의 주제다.
